# AGENTS.md

Conventions for working in this repo, for humans and coding agents. See [README.md](README.md) for setup.

## Language

**The app is Polish.** Everything a user sees is in Polish: UI text, API error messages (`ValidationError`, `PermissionDenied`, ...), push notification titles and bodies, dates (`pl-PL`) and plurals (Polish has three forms; use the helper in `frontend/src/lib/`, don't write `n === 1 ? ... : ...`). New user-facing strings must be Polish; don't add English ones, and don't introduce an i18n framework unless asked. Code, identifiers, comments, commit messages and these docs stay in English. Use the established terms: *głosowanie* (vote/poll), *weto* (veto), *oddaj głos* (cast vote), *Zarządzanie* (management), *Sejmik* (the voting section), *posłowie* (participants), *wnioskodawca* (poll creator), *obrady* (ongoing votes).

## Layout

```
backend/    Django 6 API (uv, Python 3.14, ASGI-only)
  config/     settings, root urls, asgi.py (no wsgi.py)
  accounts/   custom User model + JWT auth endpoints
  core/       health check, SSE channel manager/helpers, middleware
  tests/      pytest-django tests
  pacts/      bets, group bets, resolutions (kinds in pacts/kinds.py)
  ledger/     Rozliczenia: shared expenses, debts, payments, balances (Tricount); pacts feed it
frontend/   Vite + React + TypeScript PWA (pnpm)
  src/components/ui/   shadcn components (generated)
.pre-commit-config.yaml, docker-compose.yml (Postgres), .vscode/launch.json (tracked)
```

## Commands

Backend (from `backend/`):

```sh
uv run python manage.py runserver      # Daphne/ASGI dev server on :8000
uv run python manage.py makemigrations && uv run python manage.py migrate
uv run pytest                          # needs `docker compose up -d db`
uv run ruff check --fix . && uv run ruff format . && uv run ty check
```

Frontend (from `frontend/`): `pnpm dev | build | typecheck | lint | format`.

All checks at once: `uv run --project backend pre-commit run --all-files`.

## General

- Keep hooks green; never bypass pre-commit with `--no-verify`. Fix the cause instead.
- Commits should only be authored by humans.
- Add dependencies with `uv add` / `pnpm add` so lockfiles stay in sync, and commit lockfiles.
- Prefer extending the existing patterns below over introducing a second way of doing the same thing.

## Backend

- **Async-first, ASGI only.** Don't add WSGI config or sync-only server assumptions. Use async views or DRF's sync views as appropriate, but never block the event loop in `async def` code (wrap ORM/sync calls with `sync_to_async`, or use Django's async ORM methods).
- **Settings** come from the environment via django-environ (`backend/.env`, template in `.env.example`). Never hard-code secrets, and add new settings with a safe default or make them required.
- **Auth** is JWT only (SimpleJWT). Endpoints are authenticated by default (`IsAuthenticated`); opt out explicitly with `AllowAny` and `authentication_classes([])`, as in `core/views.py`.
- **User model** is `accounts.User`. Always reference it via `settings.AUTH_USER_MODEL` / `get_user_model()`, never `django.contrib.auth.models.User`. People are identified by **username only** (no name or email fields). Profile pictures live in `User.avatar`; set/replace/remove them only via `User.set_avatar` / `clear_avatar` and `accounts.avatars.process_avatar` (validates, square-crops, re-encodes to WebP). Files are served from `MEDIA_URL` (`/api/media/`, so the dev proxy covers it); in production the web server must serve `MEDIA_ROOT` there.
- **Migrations:** one logical change per migration, generated with `makemigrations`, reviewed, and committed with the model change. Never edit an applied migration; add a new one. CI/pre-merge should be clean under `makemigrations --check --dry-run`. Ruff skips `*/migrations`.
- **API shape:** serializers for all request/response bodies so drf-spectacular generates an accurate schema (`/api/schema/`). Keep URLs under `/api/`, with trailing slashes.
- **SSE:** push events with `core.events.notify_user(user_id, event_type, data)`. Channels are per user (`user-<id>`) and `/api/events/` is JWT-authenticated by `core.middleware.EventStreamJWTMiddleware`. Listeners are in process memory, so cross-process publishing needs `EVENTSTREAM_REDIS`.
- **JSON only:** the API accepts and returns JSON (multipart only on file-upload views, via an explicit `parser_classes`). Tests post JSON by default.
- **Voting** (`backend/voting/`): polls are typed by `Poll.kind`; everything kind-specific (config/ballot validation, what a veto means, result and tone) lives in a `PollKind` in `voting/kinds.py`, registered with `register()`. To add a vote type (yes/no, options) add a kind there plus its UI in `frontend/src/features/voting/kinds/`; models, endpoints and the generic screens don't change. All state changes go through `voting/services.py` (locked, validated, events sent on commit). **Ballots are hidden until a poll ends**: that rule lives only in `PollDetailSerializer`, and SSE events carry ids only so clients refetch. Everyone can read every poll; only participants vote and get push. User stats only count closed polls.
  **Profile votes** (`nickname`, `avatar`) are score kinds that change another member's profile: everyone votes, the creator can't target themselves, end them early or be vetoed (`allows_veto`), and they pass at an average of at least 1 with no veto. The change is applied by the kind's `on_close` hook (a failure is recorded in the result as `applied=false`, never raised). A proposed picture is stored on `Poll.proposed_avatar` and deleted when the poll closes. **Deadlines:** every poll ends 72 h after creation (`services.POLL_DURATION`), with push reminders to non-voters at 24/48/69 h. Nothing runs this by itself: schedule `uv run python manage.py process_deadlines` (runs the poll and pact jobs) every ~5 minutes (cron or a systemd timer).
- **Pacts** (`backend/pacts/`, tab "Zakłady"): like polls, typed by `Pact.kind` with everything kind-specific in a `PactKind` in `pacts/kinds.py` (`register()`); all state changes go through `pacts/services.py`. Kinds: `bet` (one wager per opponent against the host, each with its own stake; the loser of a wager owes the winner that stake; wagers accept, settle and fail independently), `group_bet` (everyone picks a side; stakes are optional: with them it is a shared pot where the winning side splits the losing side's stakes pro rata and nobody loses more than their stake, without them it is a plain prediction that only scores who was right; starts once every invitee has answered) and `resolution` (host commits, nobody is invited, no money: every other member judges in a `resolution_judgment` Sejmik vote, called by anyone once the deadline has passed; a strict majority decides, a tie or no votes leaves it open). Invitees must accept (group bets take side/stake on accept). **Every pact except a resolution takes join requests** from any member (`JoinConsent`): the host approves for a `bet`, every active participant for a `group_bet`. **With a deadline, nobody can call a result before it passes** (`services.result_allowed`, exposed as `actions.can_set_result`); until then the only possible claim is `{"void": true}`, which calls it off. An outcome claim (`OutcomeProposal`) settles once every required party confirms; a dispute can be escalated to a `pact_ruling` poll (`voting/kinds.py`) voted on only by members outside the pact, where a strict majority upholds the claim (applied in `on_close`, like profile votes). **Every member can read every pact** (like polls); only participants act on one (403 otherwise). Each change is broadcast over SSE (`pact.created` / `pact.updated`, ids only) to everyone; push goes only to the people it concerns. **Money** never lives in pacts: settling hands the kind's `settle()` debts (`ledger.money.Debt`) to `ledger.services.record_debts`, one ledger entry per settlement; a note-only stake on a `bet` / `group_bet` becomes a 1-item goods debt (group bet: each losing-side note-staker owes one item to the winning side in turns). Stats (`pacts/stats.py`) come from confirmed claims' `verdicts` plus the money obligations of pact-sourced ledger entries (goods ignored); there is no public ranking, they are only shown to administrators as `pacts` on the managed-user payload (the profile page in the management panel). `process_pact_deadlines` (run via `process_deadlines`) marks overdue pacts, nudges weekly and expires invites after 7 days. **TEMPORARY:** superusers can create a pact as another member (`creator_id` on `POST /api/pacts/`, `backfill` in `services.create_pact`, a "Utwórz jako" selector on the new-pact form) to enter old pacts by hand: the deadline may be in the past, invitees are already in with their terms, nobody is notified. Remove all three together. **Attachments** (`PactAttachment`) are pictures that supplement a pact's notes: any participant can add up to 10, only via `pacts.services.add_attachment` and `accounts.avatars.process_photo` (validates, keeps the aspect ratio, caps the longest side, re-encodes to WebP, strips EXIF); the uploader or the pact's creator can remove them. Like avatars they are served from `MEDIA_URL`, so anyone with a URL can open the file.
- **Ledger** (`backend/ledger/`, tab "Rozliczenia"): a Tricount for the single global group (every member), built in three layers. An **entry** (`LedgerEntry`) is what happened; its kind (`entry.kind`, an `EntryKind` in `ledger/kinds.py`, `register()`) validates its JSON `details` and derives its **obligations** (`Obligation`: debtor owes creditor `amount` base-currency minor units, or with `item` a quantity of goods); **balances** (`ledger/balances.py`) are aggregates over the obligations of `confirmed` entries. Kinds: `expense` (payers + items, each item split `equal` / `shares` / `exact` among its own people; a plain expense is one item; anyone may edit or delete it), `income` (a negative expense: `IncomeKind` is `ExpenseKind` with `SIGN = -1`; same details, `payers` are who received the money, the breakdown stays positive and only the nets flip), `debt` (exactly the debts given: a pact settlement via `record_debts`, or one a member records as either party, money in any currency (converted like an expense) or goods; editable and deletable by the creditor; a pact's can only change through the pact) and `payment` (pending until the receiver confirms or rejects; the payer can cancel; its obligation runs receiver -> payer, which is what pays the debt off). All arithmetic is in `ledger/money.py` (pure, no Django): `allocate` (largest remainder; every input sorted by user id so results are deterministic), `split_items` (an expense's items divided among their people; the odd grosze go to whoever is furthest behind their exact share so far across the whole receipt, ties to the lower user id, so a receipt that divides evenly does) and `settle_up` (greedy biggest debtor to biggest creditor, at most n-1 transfers), used both to turn an expense's nets into obligations and to suggest who pays whom. **Only confirmed entries count**: deleting an expense is cancelling it, nothing is ever deleted. **An expense's obligations are not an explanation** (with several payers the pairing is arbitrary); its `breakdown` (paid/owed per person) is. Money is settled across the group, goods per pair and per item (case-insensitive), never against money; suggestions assume pending payments go through and those are listed separately. **Currencies**: balances are in `money.BASE_CURRENCY` (PLN, a constant: changing it would reinterpret history); an expense in another currency (`money.CURRENCIES` with minor-unit exponents) is converted once at the top with the ECB rate for its date from Frankfurter (`ledger/rates.py`, cached for good in `ExchangeRate`, except today's before publication). Rates are fetched before any lock; the form warms the cache via `GET /api/ledger/rates/` because DRF views share one thread under ASGI. All changes go through `ledger/services.py` (locked, `version` bumped; editing requires the `version` you edited, else 409); `record_debts` is the only API other apps use, and the ledger never imports them. Every entry carries an `actions` block from `EntryKind.check`. Everyone reads everything (`GET /api/ledger/entries/`, cursor-paged by date, filterable by `kind` and `source_type`/`source_id`); `ledger.updated` is broadcast to all, push goes to the people involved, worded by the kind. **Categories** (expenses only) are the fixed `LedgerEntry.Category` choices, each with an emoji icon in `LedgerEntry.CATEGORY_EMOJI` (kept apart from the name, served by `/api/ledger/meta/`); add a category in code, with its emoji (a test checks every one has one). **Stats** (`ledger/stats.py`, `GET /api/ledger/stats/?start=&end=`, no dates = all time) cover confirmed expenses, incomes and money debts in the base currency, converted through `ExpenseKind.base_breakdown` like the balances: spent = expenses and debts minus incomes (a refunded ticket counts nothing). Money debts are a stats-only category, `debts` / "Długi" (an expense the creditor paid for the debtor: it adds to the total, the creditor's `paid` and the debtor's `share`); goods debts and payments are not spending. Per category (net, biggest first), per person (`share` = their part, `paid` = what they paid out) and a series zero-filled per day (up to 62 days) or per month. **Attachments** (`EntryAttachment`, receipts) work like pact attachments (max 10, `process_photo`; the uploader or the entry's author removes them).
- **Tricount import** (`ledger/tricount.py`, `services.import_tricount`, `POST /api/ledger/import/preview/` and `/api/ledger/import/`, superusers; UI at `/manage/tricount-import`): reads the raw JSON from `tricount-exporter --save-response` (`NORMAL` -> expense, `INCOME` -> income, `BALANCE` -> payment, `DELETED` skipped). The admin maps every Tricount name to a distinct member; the payer authors each entry and everything counts at once (payments are confirmed straight away). It is quiet (no push, one `ledger.updated` broadcast) and all-or-nothing. Entries carry `source_type="tricount"` and Tricount's entry id as `source_id`, so importing again skips what is there. Amounts use the entry's original currency (`amount_local`), converted by the ledger's own rate; payments are converted to PLN. Pictures are not imported.
- **Receipt OCR** (`ledger/receipt_ocr.py`): Gemini structured output (`GEMINI_API_KEY`, `GEMINI_MODEL`, default `gemini-flash-latest`, both optional) into the all-optional `Receipt` schema; amounts are decimals as printed, not minor units. A 503 is retried twice (`MAX_RETRIES`). `POST /api/ledger/receipt-ocr/` (multipart `image` + client `job_id`) blocks until done and sends `ledger.ocr.request {job_id, attempt}` to the caller only, right before each request to Gemini; the form's `ScanProgress` bar (`features/ledger/expense/`, events routed by `ocrBus.ts`) fills a quarter a second after each, and to 100% on the response (the HTTP response is authoritative, the SSE channel is not reliable). Try it from the shell with `uv run python manage.py test_receipt_ocr [path]` (default: `image.jpg` in the repo root).
- **Birthdays** (`accounts/birthdays.py`): `User.birthday` (a date, optional) is set by superusers in the management panel. From 20:00 Warsaw time on the day, `process_birthdays` (run by `process_deadlines`) pushes a reminder to every other member, once (`birthday_reminded_on`); 29 February counts as 28 February in years without one. `GET /api/auth/birthdays/` lists today's birthday people: the frontend dresses the whole app in the `birthday` theme, or `birthday-dusk` when the user picked a dark theme (`birthdayFor`; an event theme in `EventThemeSync`, below the calendar seasons) and `UserAvatar` gift-wraps their picture (`.gift-wrap` in `index.css`) everywhere.
- **Web Push** (`backend/push/`): needs `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_SUBJECT` (`uv run python manage.py generate_vapid_keys`); without them notifications are skipped and the frontend hides the toggle. Delivery runs on a small thread pool after commit. The service worker is `frontend/src/sw.ts` (vite-plugin-pwa `injectManifest`, no precache manifest); it needs HTTPS off localhost. It is push-only: don't add caching or a fetch handler to it, freshness comes from HTTP caching in `frontend/nginx.conf`.
- **ty and Django models:** ty has no Django plugin, so `voting/**` has a few type rules switched off in `pyproject.toml` (model fields are typed as `Field` objects). Prefer narrow `# ty: ignore[rule]` elsewhere.
- **Tests:** pytest-django, tests in `backend/tests/`, shared fixtures in `conftest.py`. Add a test for every endpoint (including the 401 case). Use `APIClient`, not mocks of Django internals.
- **Typing:** annotate function signatures. `ty` is beta; if it reports a false positive, use a narrow `# ty: ignore[rule]` with the specific rule, not a blanket ignore.

## Frontend

- TypeScript `strict`. No `any`; type API responses explicitly (ideally generated from `/api/schema/`).
- Use the `@/` import alias for `src/` instead of long relative paths.
- **UI:** Tailwind v4 (CSS-first, config lives in `src/index.css`, no `tailwind.config.js`). Add components with `pnpm dlx shadcn@latest add <name>`; they land in `src/components/ui/` and are excluded from oxlint. Prefer composing them over editing them. One deliberate edit: the `ghost` and `link` variants of `Button` are always underlined, so text buttons read as buttons; use `Button` for any clickable text instead of styling a bare `<button>`. Dropdowns in forms are `components/SelectField.tsx` (the shared `Select` at form size; options can carry an `icon`, and `display="icon"` shows only the icon in the trigger), never a native `<select>`. Use `cn()` from `@/lib/utils` for conditional classes.
- **Data fetching:** TanStack Query for all server state, with caching off on purpose (`staleTime: 0`, `gcTime: 0` in `src/main.tsx`): always-fresh data matters more than saved requests. Don't add `staleTime`/`gcTime` to queries. No fetching in `useEffect`. Routing is React Router (`src/App.tsx`).
- **Auth/SSE:** send `Authorization: Bearer <access token>` on API calls. Native `EventSource` can't set headers, so use a fetch-based SSE client for `/api/events/`.
- **Pacts UI** (`src/features/pacts/`, tab "Zakłady"): mirrors the backend kinds. `features/pacts/kinds/` has one file per `PactKind` (label, where stakes come from, which outcome claims exist and how to word them); the generic screens (`PactsPage`, `PactNewPage`, `PactDetailPage`) never branch on the kind key beyond that. What the signed-in user can do comes from the server's `actions` block on the pact, so don't re-derive permissions in the UI. Money travels as integer grosze: use `formatMoney` / `parseMoney` from `lib/money.ts`. SSE `pact.*` / `ledger.*` events invalidate the `['pacts']` / `['ledger']` queries in `features/voting/realtime.tsx`. A disputed claim becomes a `pact_ruling` poll; its UI is `features/voting/kinds/ruling.tsx`.
- **Ledger UI** (`src/features/ledger/`, tab "Rozliczenia" at `/ledger`, entries at `/ledger/:id`, forms at `/ledger/new/expense|income|debt` and `/ledger/:id/edit`, all in `pages/EntryEditorPage.tsx`): mirrors the backend kinds. `features/ledger/kinds/` has one kind object per `EntryKind` (`*.ts`: label, icon, status wording, feed summary, action labels) plus its detail component (`*Detail.tsx`); expense and income share one (`kinds/shared.ts`, worded by `expense/wording.ts`). `kindOf(entry)` is the only lookup and the generic screens (`EntryRow`, `LedgerEntryPage`, `EntryActions`) never read `details` themselves. Buttons come from the entry's `actions`. The tab offers Wydatek / Przychód / Dług as three equal buttons. Forms are built from `features/ledger/form/` (`AmountField` hero with currency and live rate, `PersonSelect`, `Segmented`, `FormSection`, `DateField`, `Extras` for the note and photos); photos picked in a form are staged and uploaded after the entry is saved. The expense form shows each person's part live beside them (`expense/split.ts` mirrors `split_items` exactly (BigInt); the server stays the authority); "Pozycjami" (a receipt) splits each line among its own people: evenly by default, or by shares or exact amounts through the line's "Po równo ▾" button (`LineSplitDialog`; the chips show each person's shares or amount, and exact amounts must add up to the line's price). The **Statystyki** view (`features/ledger/stats/`, a third segment next to Wpisy and Bilans) is lazy-loaded because of Recharts (shadcn `components/ui/chart.tsx`): a `PeriodPicker` (month or year with arrows, all time, any two dates; `period.ts` maps them to dates), summary cards, a bar chart over time, a category donut with its list (`stats/colors.ts` gives every category a fixed colour) and per-person bars. Amounts are in the entry's currency (`useMoney()` knows each currency's exponent from `/api/ledger/meta/`); balances and obligations are in grosze.
- **Themes vs. color:** a theme (`src/themes/<id>.css`) is styling only; its palette is derived from one base hue, `--base-hue` (oklch hue 0-360), e.g. `oklch(0.26 0.15 var(--base-hue))` or `calc(var(--base-hue) + 45)` for related hues. The user's hue and saturation are remembered **per theme** (`src/themes/color.ts`, localStorage `base-hue:<theme id>` / `base-chroma:<theme id>`, set inline on `<html>` by `ThemeProvider` together with the theme; unset falls back to the theme's default in CSS). The account panel has the pickers; from the console `setBaseColor(150)`, `setBaseColor('#2a9d8f')` or `setBaseColor()` change the theme on screen. Vote tones and a theme's identity colors (royal's gold, christmas, halloween) stay fixed. **Seasonal themes** (`getSeasonalTheme` in `themes/index.ts`: capybara on 10 July (light or `capybara-dusk`, to match the tone of the theme the user picked), easter from Palm Sunday to Easter Monday, polska on 1-3 May and 11 November only, christmas in December, halloween 17-31 October) are not in the picker (capybara is, together with its evening variant `capybara-dusk`: they are also normal choices), lock it while active, and may draw decorations in `EventThemeSync` (`SnowLayer`, `HalloweenLayer`, `PolandLayer`, `EasterLayer`, `CapybaraLayer`) and dress the header avatar (`UserAvatar decorated`: halloween's pumpkin, polska's flag badge, easter's bunny ears, capybara's orange, christmas's Santa hat).
- **PWA:** configured in `vite.config.ts` (vite-plugin-pwa). Icons in `public/` are generated from the root `logo.png` (`pwa-*`, `maskable-512x512.png` padded on the theme color, `apple-touch-icon.png`, `favicon.png`). Dev proxies `/api` to `localhost:8000`, so use relative `/api/...` URLs.
- **Motion:** use the shared system in `src/components/motion/` (read its `README.md`): tokens and `animate-*` utilities in `src/index.css`, `Stagger` / `Reveal` / `PageTransition` / `Skeleton` / `useCountUp` / `useFlashOnChange`. Animate transform/opacity only, take colors from theme tokens, and don't add a second animation approach. Reduced motion is handled globally in `index.css`.
- Format with oxfmt and lint with oxlint (config in `frontend/.oxfmtrc.json` and `.oxlintrc.json`). Don't add ESLint or Prettier.

## Deploying

`scripts/deploy.sh` (see [README.md](README.md#deploying)) is the only supported way to deploy: `master` is production, no tags. It keeps at most 3 DB snapshots in `backups/`, rolls back code (never the DB) on a failed launch and installs the `process_deadlines` cron job. Keep it shellcheck-clean and idempotent, and don't add a second deploy path.

## Gotchas

- Local Postgres is on host port **5434** (5432/5433 are commonly taken).
- If oxlint or oxfmt fail with "Cannot find native binding", run `pnpm install --force` in `frontend/`.
- If the ty editor extension reports unresolved imports after changing dependencies, restart its server.
